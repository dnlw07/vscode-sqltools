# Executing Queries

You have 3 methods to execute queries. Run from selection, run from bookmarks, run from history.

**TIP**: You can also set a connection to run queries against it in the first line of the file using `-- @conn ConnectionName`.

In SQL files that use query blocks, `-- %% ConnectionName` starts a block assigned to that connection. Moving the cursor into the block switches the active connection, and running the current query uses the same connection. A bare `-- %%` starts an unassigned block and falls back to the file or active connection.

## Running from a file/selection

1. With an open file, select the queries you want to run.
2. Select `SQLTools: Run Query` from command palette.
3. Wait for the results to show up.

## Running from bookmarks

1. Select `SQLTools Bookmarks: Run` from command palette.
2. Pick the query you want from the list.
3. Wait for the results to show up.

## Running from history

1. Select `SQLTools History: Run` from command palette.
2. Pick the query you want from the list.
3. Wait for the results to show up.

## Blocking SQL patterns

Set `sqltools.blockedSqlPatterns` in user or workspace settings to a list of
JavaScript regular expressions. The default is an empty list. For example:

```json
{
  "sqltools.blockedSqlPatterns": [
    "drop\\s+table\\s+(?![^\\s.]*_uat\\.)[\\w]+\\.[\\w]+"
  ]
}
```

Expressions are case-insensitive. If one matches, SQLTools blocks the whole
submitted script, shows a warning, and does not open a new results view. An invalid
expression blocks execution and reports its position in the list. SQLTools
checks the SQL after parameter substitution and ignores comments and string
literals for matching; quoted identifiers remain present. Adapt expressions to
the quoting and syntax of the database being used.

The policy is also passed to updated supported drivers for SQL generated by
SQLTools, including grid edits and metadata queries. Broad expressions can
prevent metadata loading or connection initialization. Install compatible
updated drivers: older or third-party drivers may not check their internally
generated SQL. A multi-step operation can run earlier auxiliary queries before
later generated SQL is blocked.

This is a client-side convenience, not a security boundary. Database privileges
remain necessary; the policy cannot control other clients, server-side
procedures, triggers, or dynamic SQL executed by the database.

## Queries with parameters

It also supports query string replacements with parameters either defined in `variables` or
provided with `inputBoxes`.

To enable query parameters replacements, you need to provide some additional configs.
In in your `workspaceFolder`, edit the file `.vscode/settings.json`. Make sure that you have
the following parameters enabled:

```json
"sqltools.queryParams.enableReplace": false, // enables string replacement.
// the following regex, will match named params in your variables files
"sqltools.queryParams.regex": "\\$[\\d]+|([@:$][\\w]+)",

// a connection example...
"sqltools.connections": [
    {
        "previewLimit": 50,
        "server": "localhost",
        "port": 5432,
        "driver": "PostgreSQL",
        "name": "MyDb",
        "group": "Locals",
        "database": "world-db",
        "username": "world",
        "password": "world123",
        "askForPassword": false,
        "variables": {
            ":name": "'%e%'",
        }
    }
]
```

In this case, when you execute your query, every word that matches `:name` will
be automatically replaced for `'%e%'`. But if you have a param like `$1`, it'll
ask you for it every time.

**NOTE**: this is just a string replacement, and therefore, you can execute
subqueries using this replacement. You can also change the query columns/filters
itself.

**TIP**: You can also set parameters for a query by preceding it with comment lines `-- @var :name = '%e%'`. Parameter values set in comments take priority over values set in the connection definition.
